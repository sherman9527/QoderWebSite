01

先把「从零」拆开：十二道工序，和它们为什么是这个顺序

顺序由依赖决定

判据只有一条：后一步是否依赖前一步已经定死的东西。定接口不依赖任何事；画界面依赖接口形状；工具循环依赖单轮闭环先跑通；评测依赖前面十一项都有产物。

调用形态是三样东西

后端配置先钉死三项：资源端点、鉴权凭据、部署名。鉴权微软给两条路，原文是「Azure OpenAI provides two methods for authentication. You can use either API Keys or Microsoft Entra ID」。走密钥时所有请求「must include the API Key in the api-key HTTP header」；走 Entra 时令牌进 Authorization 头，「must be preceded by Bearer」，并且要先给身份装上 Cognitive Services OpenAI User 角色。端点从资源属性里读，一条 CLI 加 jq 就能取。

部署名不等于模型名

微软把这点列为两家接口的关键差异：「you need to refer to the deployment name rather than the underlying model name in API calls」，并补一句「OpenAI only requires the model name. Azure OpenAI always requires deployment name, even when using the model parameter」。要紧的地方在于模型版本挂在部署下面，进 URL 那一段是你起的部署名；门户建部署时提示「Choose a name carefully」，因为「The deployment name is used in your code to call the model」。

S012

api-version 是契约

官方定义写得很硬：「The API version indicates the contract that you use to interface with the model in code」。REST 用查询参数指明它，取值形如 2024-06-01，全按日期排。SDK 那侧更该记住：「Azure SDK versions are usually paired with specific API versions, but you can specify the API version you want to use」——升 SDK 通常顺带换了契约，所以它要落在配置里。微软也说旧节奏结束：自 2025 年 8 月起可选用 v1，而「api-version is no longer a required parameter with the v1 GA API」。

S011S013S014

前端不直连的三条硬理由

一、密钥：凭据要进请求头，而任何进了浏览器的字符串都等于公开。二、审计与限流：速率按部署配额限（配额值换算成每分钟 token 数，1 等于 1,000 TPM），前端直连把所有用户压成同一个来源，超支分不清是谁。三、重试与成本没有单一落点：超时、退避、截断历史、记用量得在同一个函数里发生，散进组件就聚不回来。

接口这一层：Azure AI Foundry 给什么，我们把「gpt-6」当成假设说清楚

门户、资源、项目：三层不是一件事

对齐名词。ai.azure.com 这个门户现在叫 Microsoft Foundry，原名 Azure AI Studio 与 Azure AI Foundry；原 Azure AI Services 改称 Foundry Tools。资源模型旧拼法是 Hub 加 Azure OpenAI 加 Azure AI Services，新拼法收敛成一个 Foundry resource 带 projects，hub 型项目只能在 Foundry (classic) 门户管。模型调用属数据面：URL 与字段名以 REST 文档为准，与门户上点过什么无关。

S021

端点形状两套，字段名一张表

GA 版 2024-10-21 把部署名写进路径、版本当查询参数；新 v1 走稳定路由 /openai/v1/chat/completions，模型改成请求体里的 model 字段，api-version 只取 v1 或 preview。鉴权两条：api-key 头传资源密钥，或 Authorization 头加 Bearer 与 Entra 令牌，scope 是 https://ai.azure.com/.default。微软口径：生产用 Entra；密钥只适合快速验证，不被企业生产接受。

区域与配额：只给查法，不给数字

区域可用性看按部署类别分表那页，行是 Model ID 加版本，列是 eastus2 这类区域名。配额在 Foundry 门户 quota 页按订阅、区域、模型看；程序化用 Usages API 查已用量、Model Capacities API 查某区域剩余部署能力。单位是每分钟 token 数，2026-05-07 起部分模型改成订阅级共享池；GPT-6 家族只有 Tier 5 与 Tier 6 默认带配额，其余要提申请。配额按订阅发放，数字写进书里就是错的。

换模型时改三处

一、模型标识：v1 改请求体的 model，旧版改路径里的部署名。二、长度字段：聊天补全用 max_completion_tokens，max_tokens 已标弃用，思考型还要加 reasoning_effort。三、路由与版本：走 deployment 路径必须带 api-version，走 /openai/v1 不带。工具与 response_format 能不能用，按新 ID 的能力行重查。

03

一次回合：提问从浏览器走到模型再走回来，路上经过谁

先分清四个进程

一次提问走过四个进程：浏览器、后端 service、模型端点、数据库。浏览器不持有真相，模型端点不认识「会话」，数据库只在工具那一步被碰到。第 5 与第 8 步之间是个环，不是流水线。

路径图

一次回合的调用顺序

  1. 步骤 1前端 POST /api/chat，附自生成的 turn_id。 浏览器｜未落盘
  2. 步骤 2按 conversation_id 取历史，ID 后端生成。 后端→数据库｜读写

  5. 步骤 5回的可能只是 function_call，回合未完。 模型｜服务端存
  6. 步骤 6查注册表，校验参数与白名单。 后端｜落工具日志
  7. 步骤 7参数绑成占位符执行，不拼 SQL。 后端→数据库｜读
  8. 步骤 8第二次请求，连同上一轮 reasoning 与 function_call_output 发回。 后端→模型｜未落盘
  9. 步骤 9答案与 usage 落库，流回浏览器。 后端→浏览器｜写

模型没有记忆，真相在后端

文档译过来是：模型没有记忆，每个新问题都要把更新后的对话记录一起发过去。所以 conversation_id 由后端生成并持久化，客户端的 ID 只当索引。Responses API 能替你存——示例里 store 为 true、可用 previous_response_id 串下一轮；那是服务端存储，不是模型的记忆。

04

拆解这件事：把「帮我看看这个订单为什么还没到」变成能执行的东西

拆解的三种形态，各有代价

计划清单是有序步骤，最直白，但表达不了并列与回退；子问题树能画出「先查再定」的分叉；DAG 编码依赖、并行与局部失败重试，代价是那张图难讲给业务方听。

ReAct 让推理与动作交替，Plan-and-Solve 先出计划再执行，Reflexion 在执行后自我反思——三种范式只约定流程，不约定中间结构。工具调用的返回块只有 type、tool_use_id、content，没有原生「步骤」字段，结构得你自己定。

S041S042S043S044

拆解结果的最小契约

拆解失败的三种典型形态
调了没有的工具handler 比对工具注册表，没命中就不跑，回失败让模型重拆
子问题互相等按 depends_on 拓扑排序，排不完即成环；这是拆错，重试改不了结构
同一问题答两次不一致question 去标点归一化，撞车就比对产出，不一致则整条作废

一次全量规划

  • 只调一次模型出计划，便宜、可提前审、条目稳定
  • 开头看不到后面的事实，查到「已签收」即作废剩余步骤

每步重新规划

  • 中途有新线索时更稳，能就地改道
  • 每步都重发已有结果，任务越长越贵
默认全量规划，某一步失败时只重写它下游那一段。

什么时候不该拆，以及给人看什么

不该拆的判据写成一行：没有任何子问题需要工具或数据库给新事实，就整题一次答完。「这个 SKU 多少钱」是单跳事实，「把结论说人话」是纯改写——拆了只是把一次生成换成多次，每多一次多一次出错机会。

展示层只声明「准备做什么」，不是模型的内心活动；每条旁边必须挂状态，否则读者判断不了它跑没跑，待办工具的 pending、in_progress、completed 三态就是干这个的。重规划的账也算得出来：请求按输入 token 计费，每轮那份启用工具的系统提示词，Claude 4.5 系在 auto 下要 346 token；历史变长也不等于信息可用，同一事实的召回随位置呈 U 形，落在中间最容易丢。

拆解步骤本身也是模型输出，必须走输出格式一章的校验、约束解码与修复回环，不能当可信输入执行。

要设 DAG 的话，设的是什么：节点、边、并行，和谁说了算

定义与环检测

DAG 即有向无环图，写的是优先级约束：A 不做完，B 不能开始。拓扑排序把顶点排成一条线，使每条边 u→v 里 u 在前。图存在拓扑序当且仅当它无环——排序写完，环检测也顺手做完了。

S051S052

节点粒度：三种切法

最细：一次工具调用一个节点，图由人写死，运行时只管调度与并发，模型只在节点里干活——可控可测，换问法要发版。中间：一个子问题一个节点，节点内模型连调几个工具，图小了、失败半径大了。最粗：一次模型推理单列成节点。

S053S054

边是数据依赖，不是执行顺序

反例：三个互不消费彼此输出的检索节点，按看着顺眼的顺序串成链。没人沿边传数据，并行度就是假的。判据：后一个节点的输入里有没有前一个的输出？没有就不该连边。正例：三条检索从 plan 同时分叉、在显式 join 处等齐，收尾约束交给 join。

S053S059

静态编排：人写死

  • 模型只在节点内干活，失败半径落在单节点
  • 固定输入可逐节点断言

模型规划：运行时生成

  • 接住没预料到的问法
  • 图可能含环，测计划合法性而非路径
多数取混合：人钉骨架，模型只填参数。

四件事在各家的名字

一、环检测：加载时先排一遍，有环就拒绝启动。二、并发上限：并行要限流，否则打爆连接池。LangGraph 把并行节点归进同一 super-step，recursion limit 默认 25 步、1.0.6 起为 1000；Airflow 用 max_active_runs 分层限。三、重试与幂等：次数与退避是配置，幂等是设计。Durable Task 说 activity 只保证至少一次执行、建议写成 upsert，Logic Apps 默认重试 4 次，而编排代码要求确定性，因为它会被重放。重放非幂等写操作等于重复扣款，Stripe 的 idempotency key 存下首次响应，24 小时内同 key 返回原结果。四、失败传播：跳过、降级、整图失败要显式声明；Airflow 有 trigger_rule，Prefect 3 有 transactions。

工具写在哪：一个函数怎么变成模型敢调的东西

一个 tool 其实是三份东西，各住各的

把「写一个工具」想成一件事是误解。真正跑起来的是三份分离的东西:给模型看的只有 name、description、parameters 三段;实现是一个普通函数,模型看不见它长什么样;而是否只读、要不要用户确认、超时多久、成本高低,属于你运行时注册表里的元数据,不进 schema。Azure Foundry 的 Chat Completions 里,工具定义被按模型训练时的语法拼进系统提示、和用户消息一起构成上下文——所以这三份天生就是分开的。

golden 答案是存期望约束而非期望字符串：该出现的实体、该调用的工具、该满足的 schema，而不是整段原文。工具层是防漂移最有力的一环——这道题必须调哪个工具、不该调哪个、调用次数上限，官方就用 Tool Selection 和 Tool Call Accuracy 这类评估器输出 Pass/Fail。选对工具通常比措辞更稳。

回归基线，与快照录制重放

同一份用例集每日跑，比较的是通过率而非结论本身，跌破阈值就报警。要分清漂移来自哪一侧：模型侧靠版本固定和 system_fingerprint 暴露，检索侧靠把命中文档冻进用例。CI 里再把模型响应缓存下来做录制重放，让流水线不依赖外部服务，失败可复现。

防过拟合、线上兜底，以及测不到什么

评测集要防过拟合：留一部分用例永不进提示词优化循环——把用例本身写进提示词是最常见的作弊，公开基准早已被污染抬高分数。线上兜底三件套：抽样人评、用户反馈自动回流用例池、改动前灰度对比。内容审核是另一道与安全相关的独立闸门（如 Content Safety，接地检测等部分能力仅英文、且不保证全拦），别把它当漂移指标。最后承认测不到什么：语义正确性无法穷尽，测试只把漂移从「不可见」变成「有阈值可见」。

上线前那一小时：十件必须做完的事，和五种会先炸的方式

十个能勾的框

  1. 密钥出仓前端与代码零密钥。 扫全历史提交而非只工作区。
  2. 两层上限请求层有超时与重试上限，回合层有最大调用次数。 两个数字在配置里读得出。
  3. 参数化查询工具落库全是绑定参数。 喂带引号分号的输入看反应。
  4. 版本固定模型版本写死，不跟 latest。 比对两次发布的版本字段。
  5. 事件兜底不认识的事件类型走默认分支。 注入一条假类型看是否断流。
  6. 修复回环校验失败先修复一次，再失败降级。 喂缺字段输出看它选哪条。
  7. 离线重放评测不依赖外部服务。 断网重跑，复现同一个数。
  8. 日志脱敏不留用户原文与工具整段返回。 按手机号形态跑正则。
  9. 成本告警单回合与单日成本各一条阈值。 监控里有指标名和数字。
  10. 回滚演练代码、配置、提示词一并退回。 写下上次演练的起止时间。
五种先炸的方式
工具循环不收敛一次回答烧掉几十次调用。数同一请求下的调用条数，多半在同两个工具间来回；架构中心建议设迭代上限。 S133
流式被代理缓冲静默很久后一次性出全文。看网络面板是否分块到达，再绕过网关 curl 对照。
幻觉出不存在的工具名报错在分发层不在模型层。把请求里的 function.name 与注册表比对。
旧资料与新数据打架答案引用的时间比库里还早。打印本轮实际进上下文的文档标识与更新时间。
把内部推理当事实读者把「我猜」当结论。查推理与终答是否同一字段渲染。
限流与注入的官方口径
429 与重试上限等待优先按 retry-after-ms，缺它才退到指数退避加抖动；SDK 默认重试 2 次，文档建议再设 5 到 10 次上限，自接重试库要先关内置。RPM 按 1 或 10 秒小窗评估，总量没超也可能被 429。 S131
注入面在工具返回官方把第三方内容里的隐藏指令称为 document attack，扫描点除用户输入还包括 tool response。 S132
