核显凭什么能跑：卡住本地大模型的不是算力，是把权重搬过来的速度

先把它写成一道除法

自回归解码一次只吐 1 个 token，但每吐一个，都要把全部权重从内存重读一遍，再读一遍当前上下文的 KV cache。llama.cpp 官方文档写明模型是完整载入内存的，内存需求等于磁盘需求，并给出 Llama 3.1 的表：8B 的 Q4_K_M 是 4.9 GB，70B 是 43.1 GB；同一页的量化表里 Q4_K_M 是 4.8944 bit/权重、Q8_0 是 8.5008 bit/权重，也就是 1 个参数分别占 0.61 和 1.06 字节，这就是 4bit 与 8bit 的通行口径。于是解码上限可以写成一条除法：tokens/s 约等于可用内存带宽除以每 token 搬运的字节数。

这条估算的四个假设，逐条写明

  1. batch=1单人对话，一次只解码一条序列。批量推理会把同一份权重摊给多条序列，这条除法不成立。
  2. 只算权重，KV cache 另加上下文越长，每个 token 额外要读的 KV 越多，速度只会比算出来的低。
  3. 用可用带宽，不用标称带宽标称值是总线极限，核显还要被 CPU 和显示分走一层。
  4. 算的是量级，不是性能承诺不含驱动与算子库差异，也不含 MoE——MoE 每 token 只读被激活的那部分专家，会明显快过这条除法。

标称带宽不等于能用上的带宽

AMD 官方给 Ryzen AI Max+ 395 的是 256-bit LPDDR5x-8000，256 × 8000 ÷ 8 = 256 GB/s；而第三方在同一颗芯片、同一份 128 GB 配置上用 llama-bench 实测，GPU 一侧只跑到约 215 GB/s。上下文那一侧也在往下拽：llama.cpp 官方仓库记录的 DGX Spark 成绩，同一个模型 batch=1、全层卸载，上下文从 2K 拉到 32K，解码从 60.85 tokens/s 掉到 48.33。

拦住独显的是容量，不是算力

反过来量 8B 这一档：4.9 GB 权重除以 215 GB/s，估算 44 tokens/s，第三方实测 42.0（Vulkan 后端），差 5%。这条链子在核显上算得通，在独显上往往轮不到它算——Ollama 官方文档写死了调度规则：模型必须整个放进单张卡的 VRAM，放不进就不在那张卡上加载。43.1 GB 比 5090 的 32 GB 还多 11 GB，5080 的 16 GB 同样装不下这一份权重；统一内存那一侧，AMD 标 128 GB、Spark 给 128 GB、M4 Max 最高也是 128 GB。所以比较的顺序是“同一个模型谁装得下”，而不是谁的跑分高：装不下就得把层推回内存，独显那条高带宽总线当场作废。

核显输在哪，为什么又不至于致命

三处劣势是真的：内存总线与 CPU 共用，256 GB/s 只剩 215 可用，显示与系统还要再占一层；软件栈年轻，同一批模型得在 HIP 与 Vulkan 两条后端之间挑，不同量化在不同后端上更快；实测记录里也写了分类：pp 是算力瓶颈、tg 是带宽瓶颈，而 prefill（读长提示词那一下）恰恰是独显的强项。不致命的原因是：8B 这一档实测就有 42 tokens/s，解码早已不缺速度，再堆算力不会更快，把带宽提上去、或者让模型塞得进去，才会。

AMD 这一族笔电：把 96～128 GB 内存划给 GPU 用，是靠什么办到的

拓扑：位宽记在内存那一栏

Ryzen AI Max+ 395 的官方规格页把内存那一行写成 256-bit LPDDR5x、最大 128 GB、最高 LPDDR5x-8000。位宽记在内存栏而不是显存栏，意思是核显直接吃这 256 bit 的口子，而不是从 CPU 那边借道：同一批焊在板上的颗粒，由 CPU 与 Radeon 8060S（官方标称 40 组计算单元、2900 MHz、FP16 60 TFLOPS）共用。于是显存上限等于出厂内存档位，装完不能再扩。AMD 给自家 Ryzen AI Halo 开发平台标的是 128 GB / 256 GB/s，整机厂可以更狠：HP ZBook Ultra 14 寸 G1a 的官方规格页写 128 GB LPDDR5x-8533 板载。ROCm 规格表把这代核显的显存一栏直接写成 Dynamic + carveout；同族在售的 Max+ PRO 495（Radeon 8065S）与 395 共用目标代号 gfx1151。

分配：Windows 硬切一块，Linux 只做映射

额度可配，但 Windows 与 Linux 走的不是同一条路，这点最容易被话术糊掉。Windows 侧的功能叫 Variable Graphics Memory，入口在 Adrenalin 的 Performance → Tuning，改完必须重启；AMD 官方 FAQ 给的示例是 128 GB 的 Max+ 395 可划 96 GB，档位除 Default / Low / Medium / High 还有 Custom 75%，并明写划过去那部分从系统角度看已是 dedicated graphics memory，不能再当系统内存——划多了 CPU 是真会饿。Linux 侧 AMD 的 RDNA3.5 优化文档更直白：这类 APU 靠 GPUVM 按进程做地址映射，没有独立 VRAM 池，GTT 默认上限约为总内存的一半（文档示例在 128 GB 机器上报 62.82 GB），且是动态映射、GPU 不用时系统能收回；同一份文档因此建议 BIOS 的专用显存保留保持很小（举的例子是 0.5 GB），要更大额度就动 pages_limit，单位是页不是 GB。

Spark 这类「CPU＋GPU 一台小盒子」和传统独显的差别，不在快，在能不能装

互连：一致性止于片内，出了片还是 PCIe

GB10 把 CPU 和 GPU 装进同一颗芯片，中间走 NVIDIA 自家的 C2C 接口。官方 Hot Chips 2025 材料把它写成「高带宽、低功耗 C2C 接口，NVIDIA NVLink 架构」，给出约 600 GB/s 聚合带宽，并写明 GPU 经它访问全部系统带宽、CPU 与 GPU 之间是硬件双向一致性，收益是省掉 Cache Management Operation 的开销。

差别不在速度，在层级。独显机里两者之间只有 PCIe 一条路，权重要先复制进显存才算 GPU 的数据；而这台盒子的对外网卡也仍走 PCIe——官方文档写 ConnectX-7 经两条 PCIe Gen5 x4 链路接入 SoC。跨机就掉回传统搬运。

内存：装得下是默认值，装不下才要设计

128 GB LPDDR5x 被官方写成「一致性统一系统内存」，256-bit 位宽，标称带宽 273 GB/s。容量边界也是官方给的：单机推理到 2000 亿参数、微调到 700 亿；两机 256 GB 到 4000 亿、四机 512 GB 到 7000 亿。

独显那侧是另一种取舍：官方对比表里 GeForce RTX 5090 为 32 GB GDDR7、512-bit、1792 GB/s，RTX 5080 为 16 GB、960 GB/s——带宽是这台盒子的 3.5 到 6.6 倍，容量只有它的四分之一和八分之一。权重装不进那 32 GB 就只有两条路：加一张卡（跨卡仍过 PCIe），或把层卸回 CPU 内存，此时决定每秒 token 数的是那条链路而非显卡算力。

精度口径：同一个 1 PFLOP，三页写得不一样

用户指南写「最高 1,000 TOPS 推理，以及 FP4 精度、带稀疏性的 1 PFLOP」；产品页规格表缩成「Up to 1 PFLOP FP4」，稀疏性没了；伙伴 PNY 的规格页用脚注补回来——「使用稀疏特性的理论 FP4 TFLOPS」。同一份 Hot Chips 材料讲数据中心 NVL72 时又特意标成「15 PetaFLOPS，稠密 NVFP4」。结论要写死：不同精度下的标称算力不能互相换算。官方给这台的另一条硬数字只有 CUDA fp32 31 TFLOPS；FP8 与 FP16 稠密算力未公开。GeForce 那张表连口径都省：3352 AI TOPS，不写精度、不写稀疏。

每年多付的电：一条乘法

年电费（元）= 平均功耗（W）÷ 1000 × 每天小时数 × 365 × 0.4883。0.4883 元/千瓦时是北京市居民生活电价一档（月 1–240 千瓦时口径），超过 240 度进二档。

代进去：AMD 395+ 按官方默认 TDP 55W、每天推理 4 小时，一年 80 度电，约 39 元；把 cTDP 拉到 120W 上限，一年 175 度，约 86 元。Spark 按官方 GB10 标称 140W 算，4 小时一年 204 度，约 100 元（第三方长测实测满载只有 100W 出头，那就更省）。Mac Studio 官方功耗表里 M5 Max 36GB 那档最大值 200W、闲置 7W：按 200W 跑 4 小时一年 292 度，约 143 元；闲置挂机一整天不到一毛钱。官方规格页另把 Mac Studio 的最大持续功率标到 480W，那是电源余量，不是常态。

所以电费不构成三条路的差异：最贵的一档一年也就一百多块，跟机型之间几千到上万的价差不是一个量级。

先分清每个数字量的是哪件事

这几条路的参数都不假，坏在它们量的是不同的事：厂商标的是算力上限，销售讲的是内存容量，评测站给的是某个模型在某种精度下的输出速度。三句各自成立，接到一起不成立。

一、TOPS 是潜在峰值，换算不出 tokens/s

Qualcomm 把 AI TOPS 写成「按 NPU 架构与所需频率得出的潜在峰值推理性能」——潜在两字是关键，它和精度档、是否计入稀疏绑在一起：NVIDIA 开发者论坛里就有帖子专门对账 Orin 标称 170 sparse INT8 TOPS 与实测的差距。微软那条 40+ TOPS 的门槛，管的是 Copilot+ 的系统本地功能，跟你要跑的开源模型无关。算力到速度之间断在哪：2026 年一项拆移动 NPU 推理效率的研究测到，同一模型换个框架，性能差最大 10 倍。

S091S094S092S093

二、装得下和跑得动是两笔账

权重字节只决定装不装得下；上下文一长，KV cache 才是内存主项，NeurIPS 2024 那篇长上下文 KV 量化的论文就是这么定位的。式子可复算：每 token 占用 = 2 × 层数 × KV 头数 × head_dim × 精度字节。Llama 3 70B 取 80 层、8 个 KV 头、head_dim 128，FP16 下约 320 KB/token：4K 上下文一条序列 1.25 GB，32K 到 10 GB，四路并发再乘四。反面同样成立——DGX Spark 的 128 GB 装得下 Llama 3.1 70B 的 fp8 权重，同机实测只有 2.66 tokens/s，瓶颈已经换成带宽。

三、量化省的是字节和带宽，不省质量

Google 发 Gemma 3 QAT 时自己讲清楚：int4 相对 BF16 是 4 倍数据缩减，而量化常带来质量下降，所以要靠训练期补偿。差多少：第三方复述 Google 的 QAT 权重在 MMLU、HumanEval 上比 BF16 低约 1%–2%；另一批实测口径更松，8-bit 距 FP16 基线 0.5% 以内，综合评测则给 4-bit 判了「大体可用」。这些数并不互相打架，它们是不同的数据集、不同的表。看到「几乎无损」，先问是哪个 benchmark。

自己复核的三步：算式、一条命令、一张表

三步：算式、一条命令、一张表

  1. 把宣传数字变成算式解码速度上限 = 有效带宽 ÷ 每 token 需读字节数；后者是激活参数量×位宽再加每 token 的 KV cache。折扣不许凭空取，要写清是谁给的口径。 上限 = 标称带宽 × 折扣 ÷ (激活参数量 × 位宽 + 每 token KV cache)
  2. 在自己机器上跑一条命令，把口径固定别用别人的分数验证自己的机器：跑之前把量化档、上下文、批大小、线程数、重复次数记在同一条，并确认首 token 与逐 token 是分开计还是合并报——名字相同不等于测量点相同。
  3. 把结果填回对照表把本机跑出的两个数填进对照表的对应格子。填不进去通常是口径错了：先怀疑量化档不是同一个、上下文被默认值截短，最后才怀疑硬件。
